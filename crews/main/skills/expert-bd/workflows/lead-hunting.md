# Lead Hunting（潜在客户探索）

从公开账号和评论证据筛选潜在客户，交付可追溯的线索与判定理由。策略 A 分析发布者画像；策略 B 从评论中提取需求。两种策略分别统计，用户要求同时使用时明确各自样本。

## 1. 确定范围

明确策略、目标平台与关键词、匹配/排除标准、最大探索量和报告形式。说明充分时直接开始；用户要求周期执行时沿用其已有配置。找客户和筛选线索不代表已授权发送，后续联络按本包 Interaction workflow 执行。

## 2. 获取候选

按平台读取并调用具体采集技能：抖音 `douyin-hunter`、小红书 `xhs-hunter`、TikTok `tiktok-hunter`、快手 `kuaishou-hunter`、X `x-hunter`、微博 `weibo-hunter`、微信公众号 `wx-mp-hunter`。搜索、账号/作品及评论读取使用各技能实际支持的命令；微信公众号评论不可得。其他支持的网站用 `smart-search` 搜索和 `browser-guide` 浏览，微信视频号目前无内容获取方案。

保留完整账号 ID、内容/主页链接、评论 ID、发布日期和本次取证时间。排序以实际返回为准，不能把默认排序写成“由新到旧”。API 平台不改走浏览器采集。

## 3. 判定与去重

读取 `expert-bd` 的 bd-record 工具说明，数据库不存在时用 `bd-record init-db`。深入读取同一对象前用 `bd-record check-creator --platform <平台> --creator-id <完整ID>` 去重，已记录对象不重复探索；用户指定复核既有对象时只补研究报告，不覆盖其联络状态。

- **策略 A**：读取公开简介与最多前 10 个作品的标题/简介，分析定位、业务、实际需求和合作适配度；排除同行与不符合标准的对象。只分析简介时写明未分析视频正文。
- **策略 B**：按约定数量读取评论，提取需求原文、公开评论者 ID/昵称、评论时间和来源；只有明确需求证据才列为潜客，个别评论不代表整体市场。缺少稳定 ID 时列为待核实，不猜测账号。
- 用 `bd-record record-creator` 保存完整平台 ID、昵称、主页 URL、qualified 和 notes（来源链接、需求证据、判定理由）。评论来源放 notes；record-creator 要求真实主页 URL，无法取得时保留在本轮待核实报告，不调用该写入命令、不把原帖当成主页。
- 批量上限与间隔遵循本轮使用的 `douyin-hunter`、`xhs-hunter`、`tiktok-hunter`、`kuaishou-hunter`、`x-hunter`、`weibo-hunter` 或 `wx-mp-hunter` 说明；限频、不可访问与采样不足分别报告，不当作无潜客。

### 企业背景补充核验（按需）

需要核验企业潜客的主体、经营状态或合作风险时，可使用天眼查 `tyc`。先遵循本包 [SKILL.md 的安装与授权规则](../SKILL.md#安装与授权规则)：先检查是否已安装；已安装直接使用，仅未安装时先展示免费额度与计费规则，再征求安装同意。

以下为独立查询示例，按任务所需选择；示例企业仅演示用法，执行时替换为已确认的目标企业全称或统一社会信用代码：

```bash
# 工商登记：企业名称、信用代码、登记状态、法定代表人等
tyc company registration-info "乐视网信息技术（北京）股份有限公司" --head 80

# 基础风险总览
tyc risk overview "乐视网信息技术（北京）股份有限公司" --head 80
```

保留企业全称、信用代码、来源（天眼查及所用命令）、查询时间和返回结果，补入 Workspace `bd/leads/` 本轮报告及线索 notes。企业与账号之间的对应关系需有证据；主体不明、无权限、额度不足和无数据分别标注，不替代需求证据或凭风险摘要判定“无风险”。`--head` 仅限制展示行数，不能把截断结果当作完整风险清单。

## 4. 交付与联络

报告保存到 Workspace `bd/leads/`。列出探索量、匹配量、跳过量、不可核实量；每条线索包含目标 ID/主页、需求原文和来源、判定理由、信息缺口与建议话题。

仅交付线索时任务到此完成。用户要求联系时，按本包 [Interaction](interaction.md) 核对已有授权、能力与历史，再预览、执行和记录。邮件联系先读取公共 `email-ops` 的 SKILL.md，按其起草、回复/跟进与发送流程执行；本探索流程不发送消息、不写已联络状态。
